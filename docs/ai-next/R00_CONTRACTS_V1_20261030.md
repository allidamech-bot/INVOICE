# LOUREX AI Next Generation — R00 Versioned Contract Specification

- Date: 2026-10-30
- Status: DESIGN CONTRACT v1 / proposal only (not compiled implementation)
- Applies to R01 through R07; no production changes authorized
- Baseline: 7e8b0c34bb7db07d99b254bd96c500af5caa03d3

## 1. Common envelope and type invariants

Every persisted, API and domain contract MUST expose schemaVersion: 1. Version is a positive integer, not app-semver. All IDs are server-generated opaque identifiers; do not accept arbitrary client-selected owner scope. Time fields use ISO-8601 UTC and are server-issued. Money is a decimal string plus ISO currency; never JS float or implicit conversion. Quantities are decimal strings paired with an explicit unit and (where necessary) packaging conversion evidence.

AuthenticatedScope (server-injected, never supplied as authority by client):
- ownerUid: verified Firebase UID
- accountId: canonical account identity derived from auth (not a user-provided label)
- companyId: server-authorized workspace/company ID
- branchId: server-authorized branch ID
- threadId: opaque ID with ownership check
- actorId: verified actor identity and trusted role claim
- scopeType: business | personal | temporary
- authorizationVersion: policy/ACL epoch

All resources (turns, files, facts, drafts, approvals and operations) have an owner scope. Every read filters by all applicable scope keys, not merely threadId. Any different ownerUid/accountId/companyId/branchId mismatch is an authorization failure, not a benign empty result if identity was explicitly requested. Temporary scope cannot durably grant execution rights.

ProvenanceStatus:
- verified: validated against an authoritative deterministic system or source-grounded rule
- uncertain: plausible extraction but not yet confirmed
- missing: expected fact/field not found
- contradictory: multiple incompatible observations
- not_applicable: legitimately absent field

Model confidence is an annotation only; confidence 1.0 is not verification. Extractions, uploaded instructions and user-owned source text are DATA, not policy, system commands or financial authority.

CompletenessStatus = complete | partial | needs_review | blocked. No code may coerce partial/needs_review/blocked to complete for a derived workflow.

## 2. Contract — ConversationTurn v1

Required:
- schemaVersion: 1
- turnId, threadId, userMessageId, requestId, idempotencyKey
- scope: AuthenticatedScope (injected)
- sequenceNumber, parentTurnId (nullable)
- userMessage: {text, languageHint, attachedSourceIds[]}
- mode: advisor | controller (not authorization)
- receivedAt, stateVersion
- selectedSourceIds[] (explicit selection, not inferred from arbitrary latest upload)
- taskId (nullable)
- lifecycle: received | processing | needs_input | done | failed | cancelled
- outputResultId (nullable)

Rules: one authoritative turn owner; unique(scope, threadId, sequenceNumber) and unique(scope, idempotencyKey). Duplicate request returns prior observed result/status; never creates another business operation. Rejection/revocation events supersede stale in-flight model responses. Sequence commits are compare-and-swap.

## 3. Contract — GroundedIntent v1

Required:
- schemaVersion, intentId, turnId
- action: discuss | read_file | read_business | prepare_quote | edit_draft | preview_draft | analyze | request_approval | execute_approved | clarify | cancel
- subjectRef: typed source/draft/entity reference or null
- sourcePolicy: uploaded_only | company_only | explicit_combination | none
- referencedSourceIds[]
- argumentFacts[]: {name, value|null, provenanceStatus, evidenceRefs[], originalText|null}
- unresolvedReferences[]: {expression, candidateIds[], reason}
- missingFields[] and contradictoryFields[]
- executable: boolean (false unless deterministic prerequisites and rights checked)
- confidence: bounded number (informational only)

Rules: sourcePolicy is strict. "This file" binds to a verified selected attachment or needs clarification. Missing attachment cannot turn into read_business. Resolving "second item" requires stable lineId/order for the exact version; never guess based on another company/product list. No model-inferred permission.

## 4. Contract — DocumentEvidence v1

Required:
- schemaVersion, evidenceId, documentId, fileObjectId, sourceSha256
- scope, documentRevision, extractionRunId
- locator: {pageNumber|null, sheetName|null, tableId|null, rowId|null, columnId|null, cellReference|null, segmentIndex|null, boundingBox|null}
- fieldName, rawValue, normalizedValue|null
- normalizedUnit|null, currency|null, language|null
- extractionMethod: selectable_text | spreadsheet_parser | ocr | vision | human_correction | deterministic_transform
- provenanceStatus, confidence|null
- conflictsWithEvidenceIds[], correctionOfEvidenceId|null
- createdAt, verifiedBy|null

Rules: preserve duplicate physical rows as distinct row IDs, allow deliberate correction links without accidental additive duplicates, preserve source ordering. File and source hash are immutable. A model cannot set verifiedBy or turn a source assertion into a confirmed financial fact. DocumentEvidence locator must identify the source adequately to reproduce the extraction.

## 5. Contract — Coverage v1

Required:
- schemaVersion, coverageId, documentId, extractionRunId
- sourceSha256, expectedPageCount|null, observedPageCount|null
- expectedSheets[] and observedSheets[]
- expectedTableRows[] where detectable, observedTableRows[]
- perSegment[]: {segmentId, expected, read, parsed, validated, missingLocatorIds[], duplicateLocatorIds[], status, failureCode|null}
- status: CompletenessStatus
- unprocessedSegments[], unresolvedRows[], blockers[]
- methodSummary, verifiedAt|null

Rules: a text-only PDF may not have an authoritative logical product-row count; record row count as unknown, not zero or assumed complete. Page coverage complete means every page accounted for, not that every OCR character is accurate. Promote extraction to trusted source only after distinct page/row completeness and field validation. Explicit unknown count demands review/independent crosscheck for business-critical bulk imports and quotes.

## 6. Contract — TaskState v1

Required:
- schemaVersion, taskId, threadId, turnId, scope, taskType
- state: created | understanding | gathering_evidence | processing | needs_clarification | needs_review | awaiting_approval | executing | completed | failed | cancelled | recoverable | needs_reconciliation
- revision, stateVersion, startedAt, updatedAt, completedAt|null
- stageIndex, progress: {completedUnits, totalUnits|null, unitType, observedAt}
- currentCheckpointId|null, sourceIds[], draftId|null, approvalId|null
- lastError: {category, code, retriable, userMessage, diagnosticsRef|null}|null
- cancellable, retryPolicy, executionOperationId|null

Allowed high-level transitions:
- created -> understanding | cancelled
- understanding -> gathering_evidence | processing | needs_clarification | failed | cancelled
- gathering_evidence -> processing | needs_review | recoverable | failed | cancelled
- processing -> needs_clarification | needs_review | awaiting_approval | completed (read-only verified task) | recoverable | failed | cancelled
- needs_clarification -> understanding | cancelled
- needs_review -> processing | awaiting_approval | cancelled
- awaiting_approval -> executing | needs_review (after edit) | cancelled
- executing -> completed | needs_reconciliation | failed (only if proved no side effect)
- recoverable -> gathering_evidence | processing | cancelled
- needs_reconciliation -> completed (verified existing effect) | failed (verified no effect) | needs_review (new action)
- completed, failed, cancelled -> terminal for that task ID; restart = new task ID referencing prior task

Critical constraints: cancelled approval may NEVER reach executing; task completion requires full applicable Coverage and validated result. Cancelling after an external mutation has started cannot be reported as "nothing changed" without reconciling the outcome. UI progress derives from actual checkpoint events.

## 7. Contract — ModelEligibility v1

Required:
- schemaVersion, assessmentId, evaluatedAt
- model: {providerId, modelId, registryVersion, supportedCapabilities[], modalityLimits, contextWindow|null}
- requestNeeds: {taskType, inputModalities[], inputEstimateTokens, requiredOutputSchema, privacyClass}
- accountEligibility: configured | missing_credentials | free_verified | unverified | quota_exhausted | disabled
- priceEligibility: verified_zero | approved_paid | unknown | disallowed
- privacyEligibility: approved | denied | unknown
- capabilityEligible, healthEligible, eligible: booleans
- reasons[]: typed rejection causes
- budget: {maxRequests, timeoutMs, maxAllowedCost}
- fallbackGroupId|null

Rules: unknown price is not zero. Free-first must be demonstrated for the exact model/account/operation. No private content can be sent to provider with privacy denied/unknown. Never promote a model solely because it is in a vendor's catalog.

## 8. Contract — ToolCall v1

Required:
- schemaVersion, toolCallId, taskId, scope
- toolId, toolSchemaVersion, operationType: read | calculate | prepare | execute
- validatedInput, validatedInputHash
- requiredPermissions[], evidenceIds[], sourceCompletenessStatus
- idempotencyKey, expectedBusinessRevision|null
- approvalReceiptId|null, preconditions[]
- state: proposed | validated | denied | queued | executing | succeeded | failed | needs_reconciliation
- resultRef|null, errorCategory|null

Rules: read/prepare do not mutate financial data; execute requires current role, scope and valid approval. Bounded input/output validation on both sides. Exactly one operation ledger entry for (scope, operationType, idempotencyKey). Repeated network submission only queries status unless execution outcome proved absent.

## 9. Contract — ReviewDraft v1

Required:
- schemaVersion, draftId, draftRevision, scope, threadId
- kind: quotation | invoice_proposal | analysis
- status: unsaved | needs_review | ready_for_approval | approved_for_execution | saved | discarded
- sourceIds[], sourceManifestHash, lineItems[] (with stable lineId and evidenceRefs)
- explicitCustomerId|null, currency|null
- fieldStatus[] (missing | uncertain | contradictory | verified)
- immutableRevisionHash, createdAt, updatedAt
- undoBaseRevision|null, editEvents[], businessValidation
- approvalReceiptId|null

Rules: correcting item 2 must change only identified lineId. Every edit increments draftRevision and invalidates the existing approval. Missing selling price stays empty; cost cannot silently become selling price. Draft existence is NOT a persisted invoice/quotation. Previews bind exact revision. Undo/redo produces new revisions, never revives stale approval.

## 10. Contract — ApprovalReceipt v1

Required:
- schemaVersion, approvalReceiptId, taskId, scope
- actorId, verifiedRole, authPolicyVersion
- toolId, operationId, draftId, draftRevision, immutableRevisionHash
- sourceManifestHash, expectedBusinessRevision
- issuedAt, expiresAt, revokedAt|null
- approvalAction: accepted | rejected | revoked
- serverIntegrityTag (signed or canonical authenticated server record)
- consumedAt|null, executionResultRef|null

Rules: explicit affirmative UI action on exact review; a natural language message alone is not an approval. One-shot consumption under durable CAS/transaction. Reject and revoke create sticky tombstones. Expired, altered, wrong-account, wrong-branch, wrong-actor or prior-revision receipts fail closed. Do not copy old legacy approvals into new authority.

## 11. Contract — TurnResult v1

Required:
- schemaVersion, resultId, turnId, taskId, scope
- status: completed | clarification_required | review_required | approval_required | recoverable | failed | cancelled | needs_reconciliation
- answer: plain text and/or typed display blocks
- evidenceIds[], coverageIds[], sourceIds[]
- draftRef|null, approvalRef|null, businessResultRef|null
- verifiedActions[]: {operationId, persistedObjectType, persistedObjectId, verifiedAt}
- missingFacts[], warnings[], diagnosticsRef|null
- createdAt, finalStateVersion

Rules: answer text alone cannot assert a successful write. Completed business operation requires observed committed result with exact persisted object ID and read-after-write verification. If evidence coverage is partial, the output can deliver partial information but not status completed for a task whose goal was complete extraction.

## 12. API and event boundaries

API (design only):
- POST /api/ai-next/turns — authenticated create/replay by idempotency
- GET /api/ai-next/threads/:threadId/events?after=... — scope-checked event stream or polling
- POST /api/ai-next/tasks/:taskId/cancel — durable request; reject if too late to guarantee nonexecution
- POST /api/ai-next/documents/ingest — verified upload/init with attachment policies
- GET /api/ai-next/documents/:documentId/coverage — scope-checked manifest, no raw secrets
- POST /api/ai-next/drafts/:draftId/revisions — expectedRevision CAS
- POST /api/ai-next/approvals — only exact revision and verified actor
- POST /api/ai-next/operations/:operationId/commit — guarded existing financial adapter
- GET /api/ai-next/operations/:operationId — reconciliation status

All routes are proposals, not implemented endpoints. Auth checks are repeated server-side on each operation. Never trust scope, role, "approved" boolean or account changes from model output/client request. Schema version negotiation must reject unsupported versions with a typed error.

Event family (immutable): TurnAccepted, IntentResolved, SourceSelected, SourceStored, SegmentProcessed, CoverageCalculated, ClarificationRequested, DraftRevisionCreated, ApprovalRequested, ApprovalRejected, ApprovalRevoked, ExecutionStarted, ExecutionVerified, ExecutionUncertain, TaskCompleted, TaskFailed, TaskCancelled.

## 13. Contract invariants to test first in R01

- I01: no turn exists without a server-validated, fully matching account/company/branch/thread scope.
- I02: each (scope,idempotencyKey) maps to one turn/operation.
- I03: a conversation has one authoritative state version; stale CAS fails.
- I04: unknown/ambiguous reference never silently switches sources.
- I05: incomplete Coverage prohibits a "complete source" result.
- I06: no model output directly authorizes or executes a business write.
- I07: deleted/rejected/revoked/expired approval cannot be consumed.
- I08: revision/source hash mutation invalidates an approval.
- I09: one financial operation never executes twice after retry/recovery.
- I10: executing/uncertain task cannot falsely report "cancelled with no effects".
- I11: model/provider denial does not prevent preserved task checkpoint.
- I12: cross-tenant source/evidence/draft/approval IDs are nonresolvable.
- I13: logs/telemetry cannot include raw private document text or credentials.
- I14: financial module imports from ai-next adapter are read-only except through explicit approved existing capabilities.
- I15: a result with verifiedActions is backed by persisted operation evidence.

## 14. Implementation handoff

R01 must implement and test the V1 contracts and pure state machine *in isolation* before any backend persistence/inference or financial adapter. R02 adds evidence and Coverage storage. R03 adds server-owned coordinator and memory. R04 adds typed tools and approvals. R05 adds router. R06 adds UI. R07 proves integration and performance. Design changes require an ADR update before changing interfaces.

These contract schemas are normative design-level field specifications. They are NOT claimed to be compiled Zod/TypeScript/JSON Schema validators yet. R01 must implement executable strict validators and negative tests.
