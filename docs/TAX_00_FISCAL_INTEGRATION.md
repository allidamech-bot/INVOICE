## Invariants and initial implementation
- src/lib/fiscal-routing.ts is the pure routing contract. Server resolves verified issuer and applicability, not the customer's country, currency, QR selection or a browser switch. Unresolved applicability or required invoice classification blocks fiscal issuance; quotes and ancillary documents do not themselves submit as fiscal invoices. A receipt or quote can still trigger a separate legal invoice obligation.
- Phase 1 generation and Phase 2 integration are distinct, with no invented approval. For Phase 2, standard documents follow clearance before delivery, simplified documents follow reporting; exceptions, retry and outage rules must be verified against current ZATCA instructions. Saudi exports and zero-rated transactions are not automatically out of scope. An international commercial document does not establish compliance in other jurisdictions.
- Route selection is not issuance authorization. The resolver is intentionally not wired into the existing app; no production behavior is changed. Verify owner/employee authorization, tenant membership, applicability, transaction classification, fiscal identity and enrollment before exposing an issue action.
- Separate compliance and production credentials by tenant and EGS unit, encrypt with managed keys, restrict access to server services, redact logs, rotate/revoke, and never include private keys/OTP/CSID secrets in browser storage or backups. No external API calls from client.
- Reserve UUID/ICV/previous invoice hash in a durable server-controlled sequence per EGS; persist signed XML, clearance/reporting response, timestamps, idempotency key, audit trail and authoritative totals. Distinguish transport ambiguity, accepted with warnings, rejected and confirmed outcomes. Reconcile crashes before retry; do not issue twice.
- Standard delivery is gated on actual clearance. Simplified issuance requires compliant signed XML/QR and a durable, deadline-aware reporting queue. Make operational statuses explicit; never show success merely because the client saved a document.
- Preserve commercial templates and original business outputs; generate compliant statutory Arabic fields and XML or PDF/A-3 with embedded XML as required, including credit/debit notes. Preserve historical documents exactly. Do not silently backfill or submit old commercial documents.
- Operational release: isolated synthetic tenant; mock/emulator race and failure tests; SDK validation; Sandbox then Simulation; credential onboarding in eligible production only after explicit owner authorization. No real taxpayer values, test invoices or secrets in repository.

## TAX-04 increment — Phase-2 lifecycle contract

Added src/lib/fiscal-issuance.ts and executable tests. It models prepared, queued, submitting, uncertain, retryable, rejected, cleared and reported states, with version checks, per-attempt correlation, immutable invoice identifiers, artifact and snapshot digests, fixed reporting deadline and output selection. First previous-invoice hash follows BR-KSA-26; later hashes use canonical SHA-256 base64. This is a pure transition module, not a server endpoint or proof of actual clearance. The caller must persist the verified artifact, EGS chain, document binding, outbox and state atomically, authenticate the actor, verify authority responses and perform version CAS in storage. State checks alone cannot prevent concurrent requests. No live API calls, new UI, rules or production changes.

Uncertain transport does not automatically replay; future adapter must reconcile and govern safe retry of the same immutable UUID/hash using authority behavior. Rejected records stay retained. Corrective re-issuance with distinct identifiers, simplified rejection remediation, clearance-disabled contingency (303), late reporting audit, phase-1 issuance, durable queue and actual cryptographic/SDK validation remain explicit release blockers. Reference: ZATCA detailed technical guideline and XML implementation standard BR-KSA-26.

## TAX-05 increment — private atomic fiscal ledger

Added api/_fiscal/ledger.js. It accepts authorized server-side scope and prepared bytes internally (no public endpoint), derives private fiscalPrivateV1 paths outside the existing recursively readable /users namespace, and uses one Admin-style transaction to create the document binding, account-scoped UUID reservation, two immutable artifact records, initial audit entry and outbox, and advance the EGS chain. The current checked-in Firestore catch-all denies client access to that top-level namespace. No rules have been uploaded or changed. Repeated identical preparation returns the existing issue; changed preparation, cross-scope access, stale EGS, stale versions and invalid SHA-256 evidence fail closed. Transitions append evidence and status audit events while updating the queue atomically. Per-artifact 512 KiB limit is an explicit interim bound to keep base64 below Firestore document limits; future object-storage and retention design must cover larger valid invoices.

Trusted caller must still authenticate and authorize account/company/EGS, prepare and cryptographically validate invoice bytes and authority evidence, enforce environment isolation, and reconcile business posting. Ledger does not verify actual XML signature or authority claims, store credentials, run a submission worker or provide a production endpoint. EGS initialization/onboarding, production Admin adapter, KMS, recovery and retention, correction path, actual Firestore emulator/security-rule tests and final-HEAD Node 24 release verification remain mandatory. The fake transaction suite serializes transactions to exercise the ledger contract; it is not a Firestore emulator or production assurance.

## TAX-06 increment — FATOORA simulation transport and onboarding gate

Added api/_fiscal/zatca-simulation.js and onboarding.js. The internal client uses only the documented fixed HTTPS simulation endpoints, V2 headers, OTP/CSR, scoped compliance and simulation operational CSID credentials, compliance checks, clearance and reporting. It refuses production environment, arbitrary destinations, redirects and credential scope/stage mismatches. Responses are bounded; transport uncertainty is not retried and raw credential errors are not logged. Onboarding gates the simulated operational CSID request on 3 or 6 distinct verified document checks (functionality maps 1000, 0100, 1100), bound to the same account/workspace/EGS/request ID/certificate digest. Failed checks require restart; no credential secrets appear in progress records.

Transport response labels are deliberately not trusted fiscal ledger transitions: the future orchestrator must validate artifacts, certificate chain, scope, authenticity, invoice identity and confirmed outcomes before posting. Unconfirmed responses, including 303, fail closed; contingency routing, definitive rejection/reconciliation, renewal and revocation still require reviewed implementation. CSR/key generation, actual SDK validation, private encrypted credential persistence/KMS, trusted onboarding state CAS, authorized commands, live simulation and production pilot are NOT complete. No public endpoint, no real OTP, no actual network call, no production activation or UI change.

## TAX-07 increment — UBL candidate, QR and cryptographic primitives

Added internal api/_fiscal/ubl-draft.js, fiscal-artifacts.js and fiscal-ecdsa.js. The restricted UBL writer produces an unsigned candidate for domestic Saudi standard 15% SAR sales with explicitly provided parties, payment means, supply date, UUID, ICV and PIH. It reuses calculateFiscalTax, escapes XML text, rejects unsupported document/line fields, and refuses discounts, adjustments, prepayments, FX, simplified invoices and correction notes rather than silently dropping data. Scope intentionally excludes other tax cases until validated. The QR codec uses UTF-8 byte lengths, ordered one-byte TLV, strict canonical base64, 700-character limit, and phase-1 and phase-2 candidate fields. Phase-2 tag 6 is the raw 32-byte hash as described by the security standard; confirm actual SDK representation with official fixtures before any activation. Local standard QR candidate is never a substitute for the authority's cleared artifact. Separate SHA-256 functions distinguish canonical XML digest (base64) from artifact bytes digest (hex). ECDSA secp256k1 primitives sign and verify exact canonical bytes with an explicit signature encoding using Node crypto; they are NOT a complete XAdES stamp or a credential store.
